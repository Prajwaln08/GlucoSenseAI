The problem

A continuous glucose monitor shows you the present — not the next two hours — and most people don't wear one at all. Can we forecast near-term glucose from cheap, ubiquitous signals, and honestly know when the forecast is trustworthy?

What I built

A complete, deployed data-science system — not a notebook. One shared feature pipeline builds both the training sets and the live serving frames, so the model trains and serves on identical features (no train/serve skew by construction).

Signature finding — reported as a headline, not a footnote

RMSE ≠ clinical safety

Treating each forecast as a hypoglycemia (<70 mg/dL) detector reveals what error metrics hide: at 2 hours the lowest-RMSE models catch fewer dangerous lows (sensitivity 0.43–0.50) than naive persistence (0.63) — they minimize squared error by regressing toward the mean, which blinds them to the extremes. Knowing where a model fails, and saying so, is the point of the evaluation.

Engineering & methods

Production engineering

  • Train ≡ serve — one feature pipeline for training and live inference; no skew.
  • Grounded forecasts — a watch gate blocks any prediction without fresh heart-rate data; no fabricated values, ever.
  • Deployed & live — Dockerized FastAPI on Render, CockroachDB Cloud with retry-aware ingest, and a self-healing cloud demo.
  • Tested & isolated — 145 unit tests green; evaluation code never touches the serving path.

Data-science methods

  • Time-series forecasting with gradient boosting (XGBoost · LightGBM · CatBoost)
  • Uncertainty quantification via split-conformal prediction intervals
  • Decision-focused evaluation — Clarke error grid, hypo/hyper event detection
  • LOSO cross-validation for honest new-user cold-start (≈24% penalty)
  • Paired significance testing (Wilcoxon) for personalization lift
  • Population drift monitoring (PSI) between training and live data
